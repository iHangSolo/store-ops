## 上下文

服装公司需要远程管理 80 家直营门店的 Windows 电脑。门店网络环境为 NAT，总部无法主动连接门店，需要门店客户端反向连接总部。项目为全新系统，采用全 AI coding 开发模式。

**约束条件：**
- 门店在 NAT 后，总部无法主动连接
- 需支持远程桌面 + 应用级控制
- 需要审计日志（合规要求）
- Windows 10/11 环境
- 全 AI coding，技术栈需对 AI 友好

## 目标 / 非目标

**目标：**
- MVP 快速上线，支持远程桌面、命令执行、资源监控、审计日志
- 架构简洁，便于 AI 生成和维护
- 门店客户端一键安装，无需复杂配置

**非目标：**
- 分组管理、角色权限（后期迭代）
- 高可用、主备部署（MVP 单机）
- 客户端自动更新（后期迭代）
- 跨平台支持（仅 Windows）

## 决策

### D1: 技术栈选择

**决策：** Go 后端 + Vue 3 前端 + Wails 客户端 + PostgreSQL

**理由：**
- Go：语法简洁，AI 生成代码质量高，单二进制部署，适合长连接场景
- Vue 3 + Element Plus：国内生态成熟，企业后台组件丰富
- Wails：内存占用低（~20MB vs Electron 100MB+），Go 贯穿前后端
- PostgreSQL：稳定可靠，JSON 字段支持好

**备选方案：**
- Python FastAPI：AI 最熟悉，但性能稍弱
- Electron：生态成熟，但内存占用高
- MySQL：更常见，但 PostgreSQL 功能更强

### D2: 远程桌面方案

**决策：** 集成 RustDesk 开源方案

**理由：**
- 开源可控，可定制无密码连接
- 成熟稳定，无需从零开发
- 支持直连 + 中继，穿透能力强

**备选方案：**
- 自建 WebRTC：完全可控，但开发量大
- TightVNC：更轻量，但 Web 端支持弱

### D3: 通信架构

**决策：** WebSocket 长连接（门店 → 总部）+ REST API（Web → 总部）

**理由：**
- 门店在 NAT 后，必须主动连接总部
- WebSocket 支持双向实时通信
- REST API 便于 Web 前端调用

**消息格式：** JSON

### D4: 客户端认证

**决策：** TOKEN + 设备指纹

**理由：**
- 实现简单，无需证书管理
- 设备指纹防盗用
- TOKEN 可随时吊销

### D5: 部署架构

**决策：** 单体服务

**理由：**
- 80 家门店规模不大
- MVP 阶段优先简单
- 后期可拆分微服务

## 风险 / 权衡

| 风险 | 缓解措施 |
|------|---------|
| RustDesk 协议变更 | 锁定版本，不轻易升级 |
| 门店网络不稳定 | 断线重连 + 心跳保活 |
| 单点故障 | MVP 接受，后期加主备 |
| Windows 版本兼容 | 仅支持 Win10/11，测试覆盖 |
